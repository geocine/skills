Herdr architecture

herdr-app (GPUI desktop client, geocine fork 0.1.16) and herdr-core (hc, the terminal runtime). Paths: core = herdr-core/crates/herdr-core/src/, app = herdr-app/src/.

Overview

Core is a runtime, not a multiplexer: it owns programs, PTYs and screen state, and draws nothing. The app is one of its clients. It draws everything and keeps its own layout. Agent status comes only from OSC 7501.

Processes

herdr-core is one binary (hc). Hidden subcommands pick the role (cli.rs:112).

Detached launch (client::spawn_detached):

  • Linux: systemd-run --user transient units (KillMode=process, lingering), or setsid when systemd is missing.
  • macOS: the core runs as a launchd one-shot job; holders run under setsid.
  • Windows: CreateProcessW with DETACHED_PROCESS | CREATE_BREAKAWAY_FROM_JOB.

Restart and update: the core sends the holder Goodbye::Handover, saves its screens and writes restart-env.json. Programs keep running.

App boot (main.rs):

  1. update::apply_on_startup
  2. core_bin::find, which tries settings, then PATH, then known directories, then the login-shell PATH
  3. use_core
  4. hc::Core::connect
  5. hc::check(hello), which checks GENERATION, core_min and the required methods
  6. open_main

If boot fails, the app opens setup::open (Install / Fix) instead of the main window.

Communication

Endpoints

  • Unix: $XDG_RUNTIME_DIR/herdr-core/<session>.sock
  • Windows: \\.\pipe\herdr-core-<USER>-<session>.sock (ACL limited to the user and SYSTEM)
  • Holder sockets: next to the client endpoint
  • App control socket: $HERDR_APP_HOME/herdr-app.sock, one JSON line per request (herdr-app do|status|ls|shot)

Client wire (wire.rs, app hc.rs)

The connection starts as JSON-RPC 2.0, one message per line. A hello {framed:true} switches it to binary frames:

0channelu32 LE
4kindu8
5lenu32 LE
9payload≤ 16 MiB

9-byte header. Channel 0 carries JSON-RPC; each attach or event stream gets its own channel.

// 1. handshake: one JSON line each way
→ {"jsonrpc":"2.0","id":1,"method":"hello","params":{"framed":true}}
← {"jsonrpc":"2.0","id":1,"result":{"core":"…","features":["automatic_input",…]}}

// 2. binary frames from here on
0  DATA             terminal bytes, either direction
1  CREDIT           viewer returns window (256 KiB start)
2  CLOSE            stream ended, with reason
3  RESIZE           u16 cols, u16 rows
4  FOCUS            viewer focus in / out
5  FACTS            json Display (colors, cell px)
6  AUTOMATIC_INPUT  engine replies, not typed by a person

Flow control: credit-based, with a 256 KiB window per stream.

  • A viewer more than 4 MiB behind gets a fresh repaint instead of the backlog.
  • A client with more than 64 MiB of unread control replies is dropped.
  • The app returns credit per byte it ingests.

How the app uses the core

  • Process and threads: the app spawns hc connect as a child. Its threads are hc-writer, fed by an mpsc so the UI never blocks; hc-reader, which routes replies and streams; and hc-stderr.
  • Calls: terminal.run|list|get|kill|label|keep|attach|read, events.subscribe, doc.get|set, machine.list and server.status. The default timeout is 10 s.
  • Input: key_down → vt.encode_key → DATA frame. Replies from the app's own terminal engine go as AUTOMATIC_INPUT.
  • Resize: Grid::fit → vt.resize + RESIZE frame. The last active viewer decides the size; observers never resize.
  • Focus and display facts: focus goes as FOCUS frames. Colors and device-pixel cell size go as FACTS.
  • Event loop: EventLines is drained every 500 ms. Every 5th tick it also lists machines.
  • Reconnect: core.closed() → retry every 1 s → reconnected() bumps core_generation and reattaches every pane.

Remote machines (machines.rs, remote.rs)

  • The core keeps one framed Line per machine over ssh -o BatchMode=yes … herdr-core connect, or a custom --via command.
  • On Unix the lines share an ssh ControlMaster; Windows has none.
  • Line states: Connecting, Connected, NeedsLogin, NeedsUpdate, Unreachable.
  • Addresses like box/t7 are routed to that machine. Its events are merged into the local stream, and attach streams are relayed.
  • In the app, on: <machine> is passed to run and doc calls, and remote_shell.rs wraps launches in the remote machine's shell.

Terminal pipeline

  1. Spawn: terminal.run sends SPAWN to the current holder, which opens a Unix PTY or a ConPTY. On Windows the ConPTY comes from the conpty.dll shipped next to hc.
  2. Parse: every output byte goes into the core's ghostty-vt screen. The screen answers queries itself, and those queries are removed from what viewers receive.
  3. Stream: on attach the viewer gets a first paint: CAN, a VT re-render of the screen and scrollback, mode 9001, the status records as OSC 7501, and a parser continuation. After that it receives the program's raw output. There are no screen diffs.
  4. Agent input: per-terminal queue (input.rs), so agent sends never interleave with each other or with a person typing.
  5. Read: terminal.read returns screen, history or stitched. Stitched scrolls full-screen apps with the mouse wheel and glues the pages together (stitch.rs).
  6. Persistence: screens are saved as screens/<addr>.snap, for kept terminals periodically and for all terminals on handover. After a crash they are rebuilt from the holder tail.

Tabs & panes (herdr-app)

Core knows only flat terminals (t7, box/t7). The app owns the grouping: spaces, then tabs, then a split tree of panes. It stores that grouping back in the core as a shared document, so every client sees the same tabs.

Lifecycle

  • Create (tab.new → AppWindow::new_tab):
    1. Make fresh ids tb… and p…, prefixed with the machine name for remote spaces.
    2. Size the new terminal from the layout (initial_size).
    3. Start it with terminal.run in the space's folder and on the space's machine.
    4. Add it with Model::add_tab, which selects it, or add_tab_unselected when focus:false.
    A tab whose only pane is a mod (new_mod_tab) starts no terminal.
  • Split, move, swap (pane.split|swap|close, Model::split / move_pane / swap_panes): these edit the tab's root tree. A new split runs on the same machine as the pane it splits.
  • Switch (tab.select|next|prev|move|rename|settle): this only changes the model. sync() then shows the selected tab.
    • sync() keeps a TerminalView attached for every pane of every tab. Only visible panes are drawn, and hidden ones are blurred. That makes switching instant and keeps kitty images, which a repaint can't bring back.
    • HiddenFit sizes the terminals in hidden tabs, so they don't reflow when shown.
  • Settle: a settled tab is put away. It leaves the lists but keeps running, and it comes back when it is shown or when one of its agents needs you.
  • Close: tab.close ends the tab's terminals in core. Model::remove_tab returns their addresses.
  • Reconcile (on every terminal.list, about every 500 ms): reconcile() drops panes whose terminal ended. It also places terminals labeled herdr.space that aren't shown yet, such as ones started by an agent, by a script, or before a restart.
  • Attention: each pane's OSC 7501 word rolls up to its tab and space by priority, blocked > done > working > idle (Model::rollup). Whether you've seen a turn is shared across clients through the herdr.seen label.

Persistence

  • Shared document: mirror::Document::capture(model) turns the spaces, tabs and pane trees into the doc herdr-app, one per machine.
    • flush_documents writes it on the background executor through mirror_sync::round, using doc.set with a version (compare-and-set). On a conflict the app reads the newer version back.
    • Fields the app doesn't know (rest) are written back unchanged, so a newer client's data survives an older client's write.
  • Private view: what this screen shows (the active space and tab, focus history, zoom, settled tabs, recent spaces) goes to view.json, not to the shared document.
  • Tab strip: the strip is a mod (defaults/mods/tabs/main.js). It reads spaces and panes, labels tabs from their agent's live title, and switches tabs with run("tab.next") on the mouse wheel. Keys and herdr-app do tab.select go through the same COMMANDS table.

UI rendering (herdr-app)

  • Stack: GPUI (gpui-pre 0.3.8, vendored with HERDR: patches), gpui-kit (base, shell) and patched taffy for flex layout.
  • Root view: AppWindow (window.rs:408) holds:
    • the chrome tree Node, from layouts/<name>.json;
    • Model;
    • terms: block → Entity<TerminalView>;
    • mod copies, each with a ShellRoot;
    • overlays: Dialog, Popup, Toast and Window.
  • Render tree: render → render_node → render_block (Terminal, Mod, Agent or Context) → render_slot. It then adds overlays, floats (window/floats.rs), movable windows, the pane_drag layer and the app-drawn titlebar. Terminals are drawn through .cached().

Terminal → pixels

  1. crates/ghostty-sys builds libghostty-vt with Zig 0.16 and generates bindings with bindgen. vt.rs::Vt wraps the terminal, the encoders, selection, search and kitty graphics.
  2. Vt::frame() returns Frame{rows: Vec<Rc<Vec<Cell>>>, cursor, bg, search_spans}. Rows that have not changed reuse the same Rc.
  3. terminal.rs::paint_grid runs inside a canvas. It caches per-row RowOps: Bg, Sprite, Icon, Text{ShapedLine} and Decoration. Text is shaped with shape_line().with_cell_positions, with optional ligatures.
  4. sprites.rs draws box-drawing, block and braille characters as exact geometry. Missing Nerd icons fall back to the bundled Symbols Nerd Font. Kitty images become RenderImage.

Redraw scheduling

  • Ingest: ingest is time-boxed to 6 ms per turn, or 250 ms for the first history replay.
  • Redraw: only when the view was shown and vt.shows_change().
  • Output clock: a shared 33 ms clock. Within 200 ms of a keystroke the view redraws immediately.
  • Synchronized output: mode 2026 is held for at most 1 s.
  • Benchmarks: bench.rs + scripts/bench.py.

Fonts & themes

Fonts: bundled Geist, Geist Mono, JetBrains Mono (the terminal default) and Symbols Nerd Font, plus fonts from the app home. Cell metrics follow Ghostty's rounding.

Themes:

  • Presets: graphite, ink, moss and paper.
  • Shipped: atom-one-dark, win98 and geocine-dark/light.
  • User themes: themes/*.json.

mods::apply_theme maps the theme to gpui-base ColorTokens, and vt::theme() supplies the terminal palette.

Mods (herdr-app)

  • Runtime: JS folders (main.js, mod.json) run in one QuickJS-JIT VM through gpui_shell::ShellRuntime. There is no DOM: scripts describe views with gpui-kit builders (div, h_flex, svg…), and Rust replays them as GPUI elements.
  • Shipped mods: defaults/mods/* (agents, tabs, files, changes, geocine, toast, menu…) are embedded by build.rs and synced at start. Frame mods are welcome, whatsnew, settings, palette and feedback.
  • The herdr host module:
    • System and file access: exec, hc, text file read/write (local or on a machine).
    • Live reactive reads: spaces, machines, agents, panes, terminals, focused, layout and window.
    • Window actions: run(command), overlays, notify, shared, window title and badge.
    The fork adds the geocine module (fork_native.rs: listDirs, walk, copyFile), used by the Files, Changes and Graph panels.
  • Lifecycle:
    • Each copy gets its own policy: read under home, write under the app home, exec and network, per-copy storage.
    • Changed files hot reload.
    • The VM restarts above 75% heap or on out-of-memory.
    • Requests go to the window: Run, OpenOverlay, SetBadge, Control…
    • On quit, mods get a 250 ms close deadline.

Adding a mod

A mod is a folder. Herdr picks it up as soon as the folder exists; there is no registry and no build step.

~/.config/herdr-app/mods/<name>/      %APPDATA% equivalent on Windows
  main.js    // required: default-exports a class extending View
  mod.json   // where it first appears
  *.js *.svg // more modules ("./ui.js"), icons

// mod.json
{ "place": "right", "size": 320, "focusable": true }   // place: left|right|top|bottom|none
import { View, div } from "gpui-kit";
import { v_flex } from "gpui-base";
import { exec, spaces, theme, run } from "herdr";

export default class Branches extends View {
  init(props, cx) {                      // once per copy
    cx.timer.every(3000, (cx) => this.refresh(cx));
  }
  refresh(cx) {
    cx.spawn(async (cx) => {               // slow work: exec / fetch
      for (const p of spaces())
        this[p.id] = (await exec("git", ["branch", "--show-current"], { cwd: p.folder, on: p.machine })).stdout;
      cx.notify();                         // re-render
    });
  }
  render(cx) {                            // re-runs on notify and on live data
    return v_flex().bg(theme().surface).children(spaces().map((p) =>
      div().id(p.id).on_click(() => run("space.select", { id: p.id })).child(p.name)));
  }
  async close(cx) { }                     // optional, 250 ms budget
}
  1. First sighting: the first time Herdr sees the folder, it docks one copy into the shown layout according to place. With "none", the mod only appears where a layout or another mod puts it. After that, the layouts decide.
  2. Placing it explicitly:
    • In a layout block: {"type":"block","content":{"mod":"<name>","props":{…}}}.
    • As a floating block, a pane header, or an overlay: openOverlay.
    • As a tab or a split: tab.new {mod} or split_mod.
    Keys can target it in a mod:<name> section of keys.json.
  3. Reload: saving any file reloads every copy in place. A broken save keeps the old version running and reports the error in herdr-app status.
  4. Verify: herdr-app check mods/<name> loads the mod, renders it once, and exits nonzero with the exact error.
  5. Shipped mods: mods in defaults/mods/ are embedded by build.rs and rewritten on every start. To change one, duplicate it with mod.clone.
  6. Lifetime: a copy starts the first time it shows, then stays alive while its block is in the layout, even when hidden. Another layout starts its mods fresh. A pane mod stays with its tab.

State & config

  • Core state: %LOCALAPPDATA%\herdr-core\<session>\ on Windows, ~/.local/state/herdr-core/<session>/ on Unix. It holds:
    • core.lock, core.json, terminals.json, docs.json, machines.json, peers.json
    • screens/, files/, execs/
    • restart-env.json, core.log, holder.log
    If the machine id changes (a cloned machine), the core forgets its terminals, peers and screens.
  • Core config: %APPDATA%\herdr-core\config.toml on Windows, ~/.config/herdr-core/config.toml on Unix. Fields: shell, history_mb, notes, resume_agents, machine_timeout, socket… Templates live in templates/ beside it.
  • App home: settings.json, keys.json, programs.json, themes/, layouts/ (+ .state/), mods/, data/<mod>/, shared.json, view.json, window.json and herdr-app.sock.

Blueprint: a desktop app with a background process per tab

This section reuses the same split for any app where each tab drives a long-running worker: an agent, a build, a language server, a browser or an indexer. Workers are long-lived, while windows come and go.

1 · Processes: three roles, not one

  • UI client. It draws, owns tab grouping and layout, and holds no worker as a child. When it quits, crashes or updates, no work is lost.
  • Broker daemon. One per user session, guarded by a lock file that records its endpoint.
    • It owns the API, the registry of workers, events, shared documents and per-worker state snapshots.
    • The first client that finds no broker autostarts it detached (connect_starting).
  • Worker host. It spawns workers, owns their pipes or PTYs, keeps a small output tail per worker, and parses nothing.
    • Because it is boring, it rarely needs restarting, so the broker can restart or upgrade without killing workers.
    • It supervises the broker: if no broker connects within a grace period, it respawns one with backoff.
    • It runs one instance per build. After an upgrade, the old host drains and exits when its last worker ends.
  • Workers. One or more per tab, each identified by a flat id (w7, box/w7).
    • Workers know nothing about tabs.
    • Each gets its own process group on Unix or Job Object on Windows, so it can be killed and swept as a tree.

2 · Launch & supervision per OS

Linux    systemd-run --user (KillMode=process, OOMPolicy=continue, linger)  · fallback setsid
macOS    launchd one-shot job for the broker · setsid for the host
Windows  CreateProcessW DETACHED_PROCESS | CREATE_BREAKAWAY_FROM_JOB · Job Object per worker
// the UI never becomes the parent: closing the window must not close the job

3 · Communication

  1. Endpoint: one per session, either a Unix socket in $XDG_RUNTIME_DIR or a named pipe with an ACL for the current user and SYSTEM. It never listens on a TCP port.
  2. Handshake: start with line-delimited JSON-RPC, then switch to framed mode, multiplexing on one connection: [channel][kind][len][payload].
    • Channel 0 carries the request/reply calls.
    • Each attached worker stream and each event subscription gets its own channel.
  3. Flow control: per-channel credit. A slow consumer gets a fresh snapshot instead of an unbounded backlog, and a client whose replies pile up past a hard cap is dropped. A frozen tab must never stall the broker.
  4. Events carry a seq. A gap produces missed plus a fresh snapshot, and a heartbeat detects dead links. Clients rebuild their state from snapshot plus events and never poll each worker.
  5. Status: workers report it in-band, the way herdr uses OSC 7501. The broker stores it as reported, and the UI rolls it up per tab by priority: blocked > done > working > idle.
  6. Remote machines: reuse the same protocol over ssh … broker connect on stdio. Addresses gain a machine prefix, and nothing else changes.

4 · Tabs ↔ workers

  • Grouping data: the UI keeps the tab model, Space → Tab → split tree → worker id. It stores it in the broker as a versioned document written with compare-and-set, so multiple windows and other clients agree. On a conflict it reads the newer version and merges.
  • Re-placing workers: each worker carries a label naming its tab or space. On every listing the UI reconciles:
    • it drops panes whose worker is gone;
    • it places labeled workers it isn't showing, such as ones started by scripts, by other workers, or before a crash.
  • View state: per-screen state (which tab is active, focus, zoom) goes to a local file, not to the shared document.
  • Closing: closing a tab is an explicit kill call. Quitting the app is not.

5 · UI side

  • Connection threads: one connection, with a writer thread fed by a channel and a reader thread that routes replies and streams. The UI thread never blocks on I/O.
  • Attachment: keep every tab's stream attached, and draw only the visible ones. Switching is instant, with no replay.
  • Ingest: time-box each turn (6 ms), coalesce redraws on a shared clock (33 ms), and redraw immediately just after user input.
  • Reconnect: when the connection closes, retry every second, bump a generation counter, then reattach every view and re-read the documents.

6 · Survival

  • Broker upgrade: the broker hands over to the new build. It saves snapshots, tells the host GOODBYE{Handover}, and passes on its environment, while workers keep running.
  • Broker crash: the host respawns the broker, and the new broker adopts the host's workers, rebuilding their state from the host's tails.
  • Kept workers: a kept worker that dies restarts with backoff (1.5 s → 60 s), and if it was an agent it resumes its session.
  • Machine identity: store a machine id. If it changes (a cloned disk), forget the registry instead of adopting workers that don't exist.
